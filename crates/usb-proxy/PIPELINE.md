# Pipelined USB over shares (protocol 5)

Agreed design, 2026-10-19. Replaces request/reply transfers and the v3 batch.

## Problem

A shared camera sits behind a network hop (WebRTC data channel or relay
WebSocket) of tens of milliseconds. Protocol 3 sent one USB transfer and waited
for its reply before sending the next, so throughput was one transfer per round
trip even though the device answers in about a millisecond. Batches helped but
still stopped at every batch boundary, and their JSON step lists hit the header
limit.

## Model: the Postgres extended-query pipeline

The controller streams operations without waiting. The exporter runs them on
USB strictly in order, one at a time, and streams a result back for each. The
controller matches results to operations by sequence number as they arrive.

- **Sync points.** The controller sends `Sync` where it needs to know that
  everything before succeeded (before a decision, at the end of a phase). The
  exporter answers `Synced` after every earlier operation has finished.
- **Stop on error.** When an operation fails (a USB error, or a failed
  assertion), the exporter reports it and then discards every later operation
  without touching USB until the next `Sync`, which it answers with the count
  discarded. The controller treats those operations as not run. Nothing queued
  behind a failure reaches the device.
- **Waiting only at real dependencies.** A tool waits for results only where it
  must decide something from them. Everything else streams.

## Assertions

`Expect { of, offset, bytes, mask, length, alternatives }` compares bytes of an earlier IN result
(`of` is its sequence number) at the exporter. A mismatch fails the pipeline
like a USB error: later operations are discarded until `Sync`. This turns
"read, check it is still X, then write" into one streamed sequence: the write
runs only if the check passed, with no round trip in between. `mask`, when
present, ANDs both sides first. The exporter compares bytes only; it knows
nothing about what they mean.

`length`, when present, requires the exact IN extent. `alternatives` allows
up to eight other byte strings of the same width under the same mask. The
length check must hold and one byte comparison must match. This permits
explicit alternate replies without accepting unrelated status combinations.
Protocol 5 requires updating controllers and reloading browser exporters.

## Wire format

Every data-path message is one [postcard](https://postcard.jamesmunns.com/wire-format)
value (serde, stable wire format 1.0): unsigned varints, length-prefixed byte
strings and one-byte enum tags. No JSON on the data path. Payload bytes are
inline byte strings, not text. Signaling (SDP exchange) is unchanged.

Messages, controller to exporter: `Hello`, `Execute { seq, device, timeout_ms,
op }`, `Expect`, `Sync { seq }`, `Goodbye`, and the owner notices (`Status`,
`Attention`, `Activity`, `ProgressStart`, `ProgressUpdate`, `ProgressDone`).
Notices are shown when the exporter reaches them, so progress tracks USB work
rather than submission. Exporter to controller: `Ready`, `Result { seq,
completion }`, `ExpectFailed { seq, actual }`, `Synced { seq, discarded }`. A
held expectation sends nothing. Between the relay and a browser exporter,
`Routed { stream, message }` carries one controller's messages; the exporter
keeps a pipeline per stream. A USB error still ends the controller's connection
after its result, as in protocol 3; a failed expectation does not.

`op` is one of `Probe`, `List`, `Open`, `Close`, `ControlIn`, `ControlOut`,
`TransferIn`, `TransferOut`, `ClearHalt`, `OwnerStatus`, `OwnerAttention`.
Endpoints and setup fields are integers; the setup request type and recipient
are small enums.

The TypeScript exporter encodes and decodes the same values with a small
postcard reader/writer; byte-exact vectors generated by the Rust types keep the
two in step.

## Flow control and deadlines

The controller keeps at most 1 MiB of payload and 4096 operations in flight;
the data channel's own buffering applies below that. Each USB operation has its
own deadline at the exporter; an expired deadline still fences the device
(completion unknown), as before, because the transfer may yet complete.

## Client API

`Client::submit` and `Client::expect` send at once and return a sequence number;
`Client::sync` waits and returns every outcome since the last sync, in order:
`Completed`, `Discarded`, `Held` or `Failed(actual)`. `Client::request` is one
operation and its sync. Flow control waits for results only when the window is
full. A canceled call fences the connection.

FujiMod sessions stream through this without new calls: every USB step is
submitted as the ff80 engine issues it, and only a read, whose reply the engine
needs, syncs. `read_memory_many` and `write_memory_many` (and the range reads
and writes built on them) stream all their commands with one sync per 1024
commands. Session-level expectations are not exposed yet.

## Removed

The v3 `Batch` operation, per-request reply waiting in the proxy client, and the
periodic latency probe before requests.
